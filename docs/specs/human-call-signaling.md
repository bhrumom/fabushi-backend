# Fabushi Human Call Signaling — Specification

Status: active
Owner: Fabushi Backend / Social Signaling
Last updated: 2026-10-05
Related task: Fabushi Desktop FBCP Phase 1 / desktop PR #27 / ADR FBCP-ADR-003

## 1. Context

Fabushi Desktop now has a Host-owned durable CallSession state machine scoped to canonical Human conversations. The current owner persists call lifecycle, reconnect generation, signaling sequence, media capability/device selection, and terminal reason, but native transport has no cross-device call signaling API. Local-only signaling would diverge across peers and devices.

## 2. Goal

Add the minimum first-party backend signaling transport needed for one-to-one authenticated Human calls while preserving Desktop Host CallSession as the product/runtime owner. The backend provides participant authorization, durable call-channel identity, ordered idempotent events, reconnect generation fencing, and bounded event replay. It does not own UI, media capture/playback, WebRTC peer state, chat history, or conversation navigation.

## 3. Non-goals

- No Telegram/MTProto/tgcalls code or identifiers.
- No public signaling endpoints.
- No media relay/TURN implementation in this increment.
- No group/room calls in this increment.
- No second chat/message store.
- No renderer-owned call truth.
- No persistence of raw media bytes or long-lived media secrets.

## 4. Requirements

- R1: All endpoints require the existing stable Fabushi account authorization and a non-empty `x-fabushi-device-id`.
- R2: A call channel is one-to-one and may be created only between accepted friends.
- R3: Client-provided `callId` is a UUID-like opaque stable identity generated by the Host; creation is idempotent only when the same creator/peer pair is repeated.
- R4: Only call participants may read or append events.
- R5: Events are globally ordered within a call by a backend-assigned monotonically increasing sequence.
- R6: Event append is idempotent by `(callId,userId,deviceId,clientEventId)`; replay with a different payload fails closed.
- R7: Every event carries a reconnect `generation`; stale generations fail. A `reconnect` event advances exactly by one generation and fences subsequent events to the new generation.
- R8: Event kinds are bounded to `transition`, `signal`, `media`, and `participant`. Payload must be a JSON object and is size-bounded.
- R9: GET replay is bounded and supports `afterSeq` so restarted/reconnected devices converge without unbounded scans.
- R10: Terminal transition events (`ended` or `failed`) mark the channel terminal; later mutation events fail closed.
- R11: Device identity is event provenance, never account ownership. Two devices for the same participant may read the same channel and append distinct idempotent events.
- R12: Existing Human direct-messaging endpoints remain unchanged.

## 5. Data model

Add `human_call_channels`:
- `id TEXT PRIMARY KEY`
- `creator_user_id INTEGER NOT NULL`
- `peer_user_id INTEGER NOT NULL`
- `generation INTEGER NOT NULL DEFAULT 0`
- `event_seq INTEGER NOT NULL DEFAULT 0`
- `terminal_state TEXT NULL`
- `created_at TEXT NOT NULL`
- `updated_at TEXT NOT NULL`

Add `human_call_events`:
- `call_id TEXT NOT NULL`
- `seq INTEGER NOT NULL`
- `generation INTEGER NOT NULL`
- `user_id INTEGER NOT NULL`
- `device_id TEXT NOT NULL`
- `client_event_id TEXT NOT NULL`
- `kind TEXT NOT NULL`
- `payload_json TEXT NOT NULL`
- `created_at TEXT NOT NULL`
- primary key `(call_id,seq)`
- unique `(call_id,user_id,device_id,client_event_id)`

## 6. HTTP contracts

### POST /api/social/calls

Body: `{ callId, targetUserId }`.

Creates an authorized one-to-one call channel or returns the existing identical channel. A reused ID with a different participant pair returns 409.

### GET /api/social/calls/:callId?afterSeq=N&limit=N

Returns canonical channel metadata and ordered events where `seq > afterSeq`. Limit is clamped to 1..200.

### POST /api/social/calls/:callId/events

Body:
`{ clientEventId, generation, kind, payload }`.

For `kind=transition`, payload may include `action` and `state`. If action is `reconnect`, generation must equal current+1 and becomes the new generation. Other events must equal current generation. Terminal states `ended`/`failed` fence future events.

Response returns the backend-assigned canonical event sequence and current channel generation/terminal state.

## 7. Security and failure semantics

- Friendship is checked on create; participant membership is checked on every read/write.
- Invalid device IDs, call IDs, event IDs, kinds, generations, payloads, or oversized JSON fail before mutation.
- Event idempotency returns the original event only when kind/generation/payload match exactly.
- Conflicting replay returns 409.
- Missing/foreign channels return 404 to avoid participant enumeration.
- Terminal mutation returns 409.
- No bearer token, object key, credential, or media secret is persisted in event payloads by this API.

## 8. Desktop integration boundary

Desktop `CallSessionStore` remains the local product owner. `FabushiNativeMessagingClient` will transport call-channel create/read/event operations using the same account credential and device header already used by Human messaging. Host sync must apply backend events in canonical sequence before projecting them into CallSession state. Renderer/Electron must not talk to the backend directly.

## 9. Verification

GitHub Actions only. Required contracts:
- create succeeds only for friends and is idempotent for identical pair;
- reused call ID with different pair conflicts;
- foreign participant read/write fails;
- same-account multi-device reads converge;
- append assigns strictly increasing sequence;
- exact replay is idempotent and conflicting replay fails;
- stale generation fails; reconnect advances exactly one;
- terminal transition fences later mutation;
- bounded `afterSeq` replay returns ordered events;
- legacy Human messaging contracts remain green.

## 10. Acceptance criteria

- AC-1: Migration and handler/routes exist in canonical backend repository.
- AC-2: Authorization, ordering, idempotency, generation, terminal and multi-device contracts are executable.
- AC-3: Exact-HEAD backend CI is green.
- AC-4: Desktop Host adapter is wired only after this API exists and is verified.
- AC-5: This increment is not considered complete media/call acceptance: voice/video capture, device permission UI, WebRTC/media transport, incoming/outgoing UX, mute/camera/screen-share and packaged cross-device E2E remain separate acceptance work.
